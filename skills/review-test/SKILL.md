# review-test

## 目的

テストコードをレビューし、正確性、可読性、保守性を評価する。

## レビュー手順

- 対象ファイルだけでなく、判断に必要なテスト対象の実装、型定義、関連コードを確認する
- 対象コードだけでは判断できない事項を、推測で断定しない
- プロジェクト固有のテスト規約がある場合は、その規約を優先する
- 明示的な修正依頼がない場合、レビュー結果を提示してから修正可否を確認する

## レビュー項目

### テスト対象

以下を確認する。

- 原則として、public な関数や method から観測できる挙動をテストしている
- 実装の内部詳細でなく、入力に対する結果や副作用をテストしている
- private な関数や method にテストが必要な場合、production コード側での責務の分割が可能でないか検討する

### テスト・ケース

以下を確認する。

- 正常系だけでなく、必要な異常系、境界値、状態遷移をテストしている
- 単一のテストが、理解可能な 1 つの挙動、またはシナリオに焦点を当てている
- テスト対象の実装をテストコード内で再実装していない
- 常に成功する assertion や、テスト対象を実行していない
- 実際に発生し得ない条件を、理由なくテストしていない

### テスト名

以下を確認する。

- テスト対象となる条件、操作、期待される挙動を識別できる
- 対象となる関数名や method 名だけのテスト名となっていない
- 現在形を基本とし、事実として観測される挙動を表している
- 読みやすく、文法的に自然な英文となっている
- 利用するテストフレームワークやプロジェクトの命名規則に従っている

### テスト・ケースの構造

- Arrange、Act、Assert の順序を基本とする
- 各段階を空行、または適切な分割によって識別できるようにする
- 長いテストや意図の読み取りにくいテストでは、`Arrange` / `Act` / `Assert` コメントを利用する
- Act に相当する主要な操作を、可能な限り一つにする

### テスト・データ

以下を確認する。

- テスト・データから、テスト条件と重要な差分を読み取れる
- テスト結果に関係しない値を過剰に設定していない
- 意味のある値を利用し、理由のないマジックナンバーやランダムな文字列を避けている
- fixture や factory によって、テストに必要な条件が隠されていない

### DRY でなく DAMP

- テストコードでは、DRY よりも DAMP（Descriptive And Meaningful Phrases）を優先する
- テストを単純かつ明確に保つための重複は許容する
- 意図を隠さずに定型的な準備処理だけを除去できる場合のみ、fixture、factory、helper、parameterize を利用してよい

### assertion

以下を確認する。

- テスト対象の挙動を直接検証している
- assertion の期待値と実際値が、利用するフレームワークの慣習に沿った順序になっている
- assertion が広すぎず、失敗した挙動を特定できる

### test double

mock、stub、fake などの test double について、以下を確認する。

- 外部サービス、時刻、乱数、ファイルシステムなどの境界に対して利用している
- test double により、テスト対象の内部実装を過剰に置換していない
- test double の仕組みが実際のインターフェースと乖離しない仕組みを利用している
- 外部への呼び出し自体が契約上の挙動である場合に限り、interaction を検証している

### 独立性と再現性

以下を確認する。

- テストの実行順序に依存していない
- 他のテストが作成した状態に依存していない
- global state や環境変数を変更した場合、テスト終了後に復元されている
- 時刻、乱数、ネットワークなどによりテスト結果が非決定とならない
- 外部サービスや共有環境がなくとも再現可能である

## コードの更新

- ユーザーが明示的に依頼または同意した変更だけを行う
- レビュー対象外の変更や、必要性のないリファクタリングを行わない
- 更新後に差分を確認し、意図しない変更がないことを確認する
